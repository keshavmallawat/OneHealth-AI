# OneHealth AI — Unified Digital Health Record Platform

A patient-centred health record platform. A patient uploads a medical report; the
system reads it (PDF text layer or Tesseract OCR), extracts laboratory values
deterministically, compares them against documented clinical reference ranges,
flags what is outside range, and produces a patient-friendly summary with a
medical disclaimer.

> **Safety.** The AI features are an informational decision-support layer, not a
> diagnostic authority. Every AI summary carries a disclaimer applied server-side.
> All sample data in this repository is **synthetic** and generated by a script —
> no real patient information is used anywhere.

---

## Architecture

```
┌──────────────┐      ┌─────────────────┐      ┌────────────────────┐
│   Frontend   │      │  Backend API    │      │   AI Service       │
│ React + Vite │─────▶│ Node + Express  │─────▶│ Python + FastAPI   │
│  TypeScript  │◀─────│   TypeScript    │◀─────│                    │
│  TailwindCSS │      │   Prisma ORM    │      │ • PyMuPDF (text)   │
└──────────────┘      └────────┬────────┘      │ • Tesseract (OCR)  │
     :5173                     │               │ • Rule-based NER   │
                               │               │ • Reference ranges │
                     ┌─────────┴────────┐      │ • OpenAI + fallback│
                     │                  │      └────────────────────┘
              ┌──────▼──────┐   ┌───────▼──────┐         :8000
              │ PostgreSQL  │   │   Storage    │
              │  (Prisma)   │   │ local │ S3   │
              └─────────────┘   └──────────────┘
                                  :3001 (API)
```

**Why the AI service does not use an LLM to read values.** A language model asked
to read numbers off a report will confidently invent them. Extraction here is
fully deterministic — alias matching, unit normalisation, then comparison against
hard-coded intervals in `ai-service/app/data/reference_ranges.py`. The LLM is used
only to *phrase* findings that were already extracted, and when it is unavailable
a deterministic generator produces the summary instead.

## Setup

### 1. Database

The project ships with its own PostgreSQL cluster so it never collides with — or
depends on — whatever is already installed on the machine.

```
Double-click SETUP-DATABASE.bat        (do NOT run it as administrator)
```

That downloads the official PostgreSQL Windows binaries (a ZIP, not an
installer), extracts them into `.local-postgres/`, creates a fresh cluster bound
to `127.0.0.1:5433`, creates the `healthcareai` database and writes the matching
`DATABASE_URL` into `backend/.env`. It installs nothing into Windows, creates no
service, needs no administrator rights, and is removed entirely by deleting the
`.local-postgres/` folder.

Afterwards, `START-DB.bat` and `STOP-DB.bat` control it.

> PostgreSQL refuses to run under an elevated account on Windows, so these must
> be launched normally rather than with "Run as administrator".

**Alternative — Docker.** If you have Docker available, `infra/docker-compose.yml`
provides the same thing (PostgreSQL on 5433, Redis on 6379):
>
> ```bash
> cd infra && docker compose up -d
> ```
>
> then set `DATABASE_URL=postgresql://postgres:password@127.0.0.1:5433/healthcareai`.

**Alternative — an existing PostgreSQL.** Point `DATABASE_URL` at it with your own
credentials. Nothing else changes.

### 2. Backend

```bash
cd backend
cp .env.example .env          # then edit the secrets
npm install
npx prisma generate           # generates the typed client (no engine binary is used at runtime)
npm run migrate               # applies migrations over plain `pg` — needs no Prisma engine
npm run dev                   # http://localhost:3001
```

### 3. AI service

```bash
cd ai-service
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # macOS / Linux
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8001
```

Check `http://localhost:8001/health` — it reports whether OCR and an LLM key are
available.

### 4. Frontend

```bash
cd frontend
npm install
npm run dev                   # http://localhost:5173
```

### 5. Demo data (recommended before a demonstration)

```bash
cd ai-service && python scripts/generate_samples.py   # writes sample-data/
cd ../backend && npm run seed                         # demo account + analysed reports
```

Seeded account: **patient@onehealth.ai** / **Demo@12345**

## Configuration

All configuration is validated at boot in `backend/src/config/env.ts`; a bad value
fails immediately with a readable message rather than a confusing runtime error.

| Variable | Default | Purpose |
|---|---|---|
| `STORAGE_DRIVER` | `local` | `local` writes to `backend/storage/`; `s3` uses the S3 implementation. |
| `AI_SERVICE_URL` | `http://127.0.0.1:8001` | Where the FastAPI service lives. |
| `REDIS_ENABLED` | `true` | Set `false` to skip Redis entirely. |
| `PII_ENCRYPTION_KEY` | — | AES-256-GCM key. Exactly 32 chars is used verbatim; other lengths are stretched with SHA-256. |
| `MAX_UPLOAD_MB` | `25` | Upload size limit. |
| `TESSERACT_CMD` | auto-detected | Only needed if Tesseract is installed somewhere unusual. |
| `OPENAI_API_KEY` | — | Optional. Without it, summaries use the deterministic generator. |

**Never commit `.env`.** Both `.env.example` files document every variable.

## Security model

- **Passwords** — bcrypt, cost 12.
- **PII at rest** — email and phone are stored as AES-256-GCM ciphertext, with a
  keyed HMAC-SHA256 hash used for lookups. Plain-text email is never stored.
- **Tokens** — 15-minute JWT access token; 7-day refresh token in an HttpOnly
  cookie, rotated on use, with the old token blacklisted.
- **Authorisation** — role-based (`PATIENT` / `DOCTOR` / `ADMIN`), plus per-record
  ownership checks. Doctors need an unexpired, unrevoked access grant.
- **Uploaded documents** — never exposed on a public URL. Locally stored files are
  served only through `GET /api/records/:id/file`, which re-checks authentication
  and ownership on every request. S3 uses short-lived presigned URLs.
- **Audit** — every upload, view, download, update and delete is written to
  `AccessLog`.
- **Rate limiting** — per-IP and per-identifier limits on auth endpoints.

## Recognised laboratory parameters

Hemoglobin · RBC · WBC · Platelets · Fasting glucose · HbA1c · Creatinine · TSH ·
Total cholesterol · LDL · HDL · Triglycerides · ALT (SGPT) · AST (SGOT)

Each result carries a status (`NORMAL` / `LOW` / `HIGH` / `UNKNOWN`), a confidence
score, the reference interval used, the basis for it (sex-specific where relevant)
and the source line it was read from. Ranges and their citations live in
`ai-service/app/data/reference_ranges.py`.

## Tests

```bash
cd ai-service && python scripts/check_environment.py  # preflight: imports + capabilities
cd ai-service && python -m pytest tests -q            # extraction + assistant safety (15)
cd backend    && npm run typecheck                    # backend types
cd frontend   && npm run build                        # typecheck + production build
node scripts/smoke-test.js                            # core pipeline, end to end (42)
node scripts/smoke-test-consent.js                    # consent, sharing, assistant (95)
```

**152 assertions in total.**

`scripts/smoke-test.js` drives the core flow against a running stack — register,
login, upload, AI processing, extraction assertions, document access control,
cross-tenant authorisation, dashboard aggregates and soft delete.

`scripts/smoke-test-consent.js` drives the collaboration half: profile
persistence and validation, clinician registration, the full consent lifecycle,
QR sharing, assistant grounding and refusals, trends and comparison, PDF export,
reminders and rate limiting. Its authorisation assertions call the API directly,
so passing proves the **server** enforces consent rather than the UI hiding a
button.

Both suites register accounts, so running them back to back would hit the signup
rate limiter. Each waits the window out by itself rather than the limiter being
loosened for the sake of a test.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `P1000: Authentication failed` | `DATABASE_URL` credentials are wrong. With Docker it must be `postgresql://postgres:password@127.0.0.1:5433/healthcareai` — note the port. |
| `P1001: Can't reach database server` | The database is not running. `cd infra && docker compose up -d`, then `docker compose ps` until it reports healthy. |
| Backend exits complaining about the environment | `config/env.ts` validated `.env` and rejected it. The message names the exact variable. |
| Upload sticks on "Analysing" | The AI service is not running or crashed. Run `python scripts/check_environment.py` in `ai-service/` — it reports the precise import that failed. |
| "The AI service is not running" on upload | Start it: `cd ai-service && .venv\Scripts\python.exe -m uvicorn app.main:app --port 8001`. |
| Image upload fails, PDFs work | Tesseract is not installed. That is expected and non-fatal — digital PDFs are read from their text layer. Install Tesseract to enable image OCR. |
| Redis warnings at boot | Harmless. The API falls back to an in-process store and keeps working. |
| Port already in use | A previous dev server is still running. `scripts/setup-and-verify.ps1` stops stale listeners on 3001/8000/5173 automatically. |

## Roadmap

Implemented since the first release: consent-based clinician sharing, QR access
grants, the access-log viewer, the health assistant, trends with report
comparison, and PDF export. See
[docs/FINAL-FEATURE-MATRIX.md](docs/FINAL-FEATURE-MATRIX.md) for what is
complete, partial and absent, stated feature by feature.

Still ahead: ABHA/ABDM integration (only the identifier field exists today),
outbound notification delivery for reminders and consent requests, password
reset, and a production deployment pipeline.

A composite health score is **deliberately not on this roadmap**: every number in
this product traces back to a document the patient uploaded, and a composite
score would not.
